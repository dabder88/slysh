- Исходную директорию `F:\ProjectsAI\Slysh-prod` не изменять до приёмки.

## 3. Этап 1. Исправить выполнение задач, отмену и завершение процессов

**Приоритет: блокирует релиз.**

Основные области: `src/slysh/api.py`, `engine_server.py`, `engine_client.py`, `batch_runner.py`, `app.py`.

### 1.1. Ввести единое управление запусками

**Почему:**

- Глобальный флаг отмены остаётся установленным и подавляет следующий `/transcribe_chunk`.
- Отдельные задания могут одновременно обращаться к общему backend.
- Отложенный результат старого запуска способен изменить состояние нового.
- Отменённое задание может снова перейти в `running`.

**Что сделать:**

- Каждому запуску задания присваивать отдельный `run_id`.
- Передавать `job_id` и `run_id` в команды обработки, отмены, прогресса и записи результата.
- Хранить отмену на уровне запуска, а не всего engine.
- Все изменения задания проверяют актуальность `run_id`.
- Поздний результат завершённого или отменённого запуска отбрасывается.
- Повторный запрос старта активного задания возвращает существующий запуск, не создавая дубликат.
- Переход из очереди в выполнение делать атомарно; отменённое задание не запускать.
- Локальный ASR и диаризацию выполнять последовательно через общий планировщик.
- Одиночные задания и пакетные задания направлять через тот же механизм.
- На первом этапе фоновые задания обрабатывать последовательно и для облака. Параллелизм не добавлять до отдельного обоснования.

**Политика записи:**

- Диктофон и запись встречи взаимно исключают друг друга.
- Во время записи новые фоновые задания остаются в очереди.
- Если при старте записи уже выполняется фоновая обработка, запись сохраняется немедленно, а её расшифровка ждёт освобождения исполнителя.
- Существующее задание автоматически не отменять; состояние ожидания показывать пользователю.

**Приёмка:**

- Отмена A → запуск B: B успешно обрабатывается.
- Отмена A не отменяет B.
- Двойной старт создаёт один запуск.
- Отменённое задание в очереди не начинает работу.
- Ответ от старого `run_id` не меняет новый результат.
- При одновременных запросах локальный backend вызывается только одним исполнителем.

### 1.2. Устранить повторный захват блокировок

**Почему:** повторные вызовы установки компонентов и загрузки обновления воспроизводимо зависают из-за вызова функции статуса под уже захваченным обычным `Lock`.

**Что сделать:**

- Разделить чтение состояния под блокировкой и формирование HTTP-ответа.
- Не вызывать повторно захватывающий lock публичный метод из защищённого участка.
- Повторный старт возвращает текущую операцию.
- Каждой длительной операции присваивать идентификатор; старый поток не может перезаписать новую операцию.

**Приёмка:** повторные и конкурентные запросы старта/статуса завершаются; создаётся одна операция; тест ограничен по времени и выявляет зависание.

### 1.3. Ограничить ожидания и закрывать дочерние процессы

**Почему:** запуск engine, HTTP-вызовы и ожидание сервера могут зависать; после возврата из `app.main()` engine оставался запущенным.

**Что сделать:**

- Ввести отдельные ограничения:
  - запуск UI-сервера — 30 секунд;
  - появление адреса engine — 60 секунд;
  - подключение к engine — 5 секунд;
  - управляющий запрос — 10 секунд;
  - отсутствие прогресса обработки — настраиваемый watchdog, по умолчанию 10 минут.
- Длительную обработку контролировать по прогрессу, не ограничивать весь большой файл коротким HTTP-тайм-аутом.
- Ожидание строки `PORT` завершать при выходе процесса и по тайм-ауту.
- В `finally` завершать сервер, запись, исполнителей и принадлежащие приложению subprocess.
- Сначала запрашивать штатное завершение; через 10 секунд завершать оставшиеся собственные процессы принудительно.
- Не завершать процессы только по PID из старого файла. Использовать сохранённые дескрипторы и принадлежность дереву процессов.
- На Windows связать дочерние процессы с жизненным циклом приложения, включая аварийный выход.

**Приёмка:** падение при старте, отсутствие `PORT`, зависший engine, закрытие окна во время обработки и повторный запуск не оставляют принадлежащих тесту процессов и занятых портов.

### 1.4. Защитить данные от второго экземпляра

**Почему:** второй экземпляр способен принять активные задания первого за прерванные.

**Что сделать:**

- Ввести single-instance блокировку, привязанную к нормализованному каталогу данных.
- Получать её до восстановления БД и запуска обработчиков.
- Второй экземпляр показывает понятное сообщение и завершает запуск без изменения БД.
- Экземпляры с разными каталогами данных разрешены.
- Восстановление незавершённых заданий выполнять только после получения блокировки.

**Приёмка:** два запуска с одним каталогом данных не создают двух владельцев очереди; разные каталоги работают независимо; аварийное завершение не оставляет вечную блокировку.

## 4. Этап 2. Исправить пакеты и выбор провайдера

**Приоритет: блокирует релиз.**

### 2.1. Объединить обработку одиночных и пакетных файлов

**Почему:** облачное одиночное задание работает, а файловый пакет пытается запустить локальный engine и падает в `cloud_only`.

**Что сделать:**

- Вынести выбор исполнителя в общий сервис.
- Сохранять настройки провайдера, модели и обработки при создании запуска.
- Изменение настроек влияет на следующий запуск.
- `cloud_only` запрещает запуск локального engine, но разрешает облачные пакеты.
- Не переключать задание автоматически на другой платный провайдер.
- Отсутствие ключа, модели или компонента обнаруживать до начала соответствующей работы.

**Приёмка:** один файл и тот же файл в пакете используют одинаковый маршрут исполнения. Проверить локальный ASR, HTTP-провайдер и Gemini CLI через контролируемые заглушки.

### 2.2. Исправить `on_error`, итоговые статусы и возобновление

**Почему:** `on_error=stop` игнорируется файловой веткой; пакет с ошибками может выглядеть полностью успешным.

**Контракт:**

- Допустимые `on_error`: `continue` и `stop`; другие значения отклоняются.
- `continue`: обработать остальные элементы, сохранить ошибки каждого.
- `stop`: после первой ошибки не запускать следующий элемент; пакет перевести в `paused` с причиной.
- Повторный запуск пакета обрабатывает незавершённые элементы с учётом `skip_completed`.
- Добавить итоговый статус `completed_with_errors`.
- Итог пакета содержит счётчики успешных, ошибочных, отменённых и пропущенных элементов.
- Если обязательный экспорт включён и не выполнен, элемент нельзя считать полностью успешным; расшифровку сохранить.

**Приёмка:** одинаковые тесты политики ошибок для файловых и YouTube-пакетов; отмена, пауза, перезапуск приложения и возобновление не дублируют уже завершённую работу.

## 5. Этап 3. Обеспечить сохранность диктофона и записи встречи

**Приоритет: блокирует релиз.**

### 3.1. Разделить запись аудио и результат распознавания

**Почему:** воспроизведён сценарий, когда ошибка облачного распознавания после остановки превращается в `completed`.

**Что сделать:**

- Хранить состояние захвата отдельно от состояния расшифровки.
- Добавить фазу `finalizing`: устройство уже остановлено, оставшиеся данные сохраняются и обрабатываются.
- Команда остановки должна быстро возвращать состояние операции, а не держать HTTP-запрос до 600 секунд.
- `completed` разрешён только после успешного завершения всех обязательных стадий.
- При ошибке ASR сохранять аудио, уже полученный текст и понятную ошибку.
- Дать возможность повторить расшифровку сохранённой записи.
- Не очищать ссылки на сессию и worker, пока worker действительно не завершился.
- Все callbacks проверяют идентификатор сессии.

**Приёмка:** отказ провайдера, зависший обработчик и двойное нажатие Stop не теряют аудио, не показывают ложный успех и не допускают записи результата в другую сессию.

### 3.2. Исправить буферизацию и временные смещения

**Почему:** запись и `flush` выполняются в чувствительных к задержкам участках; массивы растут через `concatenate`; паузы теряют доли секунды; обработчики могут конкурировать.

**Что сделать:**

- Callback устройства только передаёт блок в ограниченную очередь.
- Запись на диск и подготовку ASR выполнять вне callback.
- Источник истины — сохранённое аудио; отставание ASR не должно увеличивать RAM пропорционально длительности записи.
- Смещения считать в целых отсчётах, переводить в миллисекунды только на границе API.
- Сериализовать pause/resume/stop и извлечение остатка буфера.
- При переполнении очереди сохранения явно остановить захват с ошибкой и сохранить доступную часть. Молча терять блоки нельзя.
- Для микрофона и системного звука проверить длительность, синхронизацию и непрерывность ресемплинга.
- После сбоя приложения обнаруживать незавершённые записи и предлагать восстановление.

**Приёмка:**

- Синтетический тест с многократными pause/resume: нет повторов, пропусков и накопления ошибки округления.
- Часовая синтетическая запись с замедленным ASR: память не растёт линейно.
- Реальные проверки микрофона, loopback и совместной записи минимум по 10 минут.
- Отключение устройства и нехватка диска дают явную ошибку и сохраняют пригодную часть записи.
- Для тестового сигнала длительность и позиции маркеров сравниваются с исходными отсчётами.

## 6. Этап 4. Защитить редактор, спикеров и экспорт

**Приоритет: блокирует релиз для потери данных.**

### 4.1. Сохранять пользовательский черновик

**Почему:** защита по фокусу textarea недостаточна; после потери фокуса polling может перерисовать несохранённый текст. Поздний ответ может относиться к уже закрытой расшифровке.

**Что сделать:**

- Хранить черновик отдельно для каждого `job_id`.
- Использовать `dirty`, а не наличие фокуса.
- Перед применением асинхронного ответа проверять идентификатор задания и поколение запроса.
- Добавить ревизию расшифровки.
- Сохранение отправляет базовую ревизию; при конфликте сервер возвращает `409`, не перезаписывая данные.
- Сохранять черновик при навигации внутри приложения; перед закрытием с несохранёнными изменениями предупреждать.
- Во время изменения сегментов активным ASR/диаризацией запретить сохранение редакторских изменений на сервер. Черновик при этом не удалять.

**Приёмка:** редактирование → blur → polling, быстрое переключение A/B, ответы в обратном порядке, ошибка сохранения и конфликт ревизий не теряют пользовательский текст.

### 4.2. Отделить идентификатор спикера от имени

**Почему:** повторное переименование `SPEAKER_00 → Alice → Bob` оставляет Alice, поскольку имя подменяет идентификатор.

**Что сделать:**

- В сегментах хранить стабильный ключ спикера.
- Имя хранить отдельно в существующей таблице спикеров.
- API возвращает ключ и отображаемое имя; UI отправляет переименование по ключу.
- Экспорт подставляет отображаемое имя.
- Переименование не заменяет текст сегментов.
- Диаризация изменяет только привязки спикеров и проверяет ревизию.
- Отказаться от восстановления старого полного снимка сегментов поверх более свежих изменений.

**Миграция:**

- Перед миграцией сделать согласованную резервную копию БД.
- Однозначные старые соответствия преобразовать автоматически.
- Неоднозначные значения сохранить как отдельные устойчивые ключи с прежним отображаемым именем.
- Не объединять разных спикеров по совпадению имени.

**Приёмка:** многократное переименование, одинаковые имена разных спикеров, Unicode, экспорт, отмена диаризации и миграция старой БД сохраняют текст и правильные связи.

### 4.3. Запретить неявную перезапись экспортов

**Почему:** два `same.wav` из разных каталогов экспортируются в один файл; первый результат теряется.

**Что сделать:**

- В автоматическом экспорте подбирать свободное имя с суффиксом.
- Проверять существующие файлы на диске и конкурирующие экспорты.
- Резервировать имя атомарно.
- Записывать результат через временный файл с безопасным завершением.
- Явная замена существующего файла допустима только после подтверждения пользователя.
- Обрабатывать недопустимые Windows-имена, завершающие точки/пробелы и длинные пути.
- Сохранять фактический путь успешного экспорта в БД.

**Приёмка:** одинаковые имена из разных папок, повторный экспорт, заранее существующий файл, параллельные запросы, отказ доступа и заполненный диск не повреждают старые результаты.

### 4.4. Исправить Markdown/YAML

**Почему:** ручное экранирование ломает Windows-пути и другие строки.

**Что сделать:**

- Использовать корректную сериализацию скалярных строк YAML; допустим JSON-совместимый строковый литерал.
- Проверить пути, кавычки, обратные слеши, переносы строк и Unicode.
- Проверять результат независимым YAML-парсером в тестах.

**Приёмка:** после экспорта и чтения метаданные полностью совпадают с исходными значениями.

## 7. Этап 5. Защитить локальный API, настройки и секреты

**Приоритет: блокирует публичный релиз.**

Отсутствие защиты локального API подтверждено прямым HTTP-запросом с чужими Host/Origin. Полная атака из браузера не демонстрировалась; не описывать её как уже доказанную.

### 5.1. Ввести аутентификацию локальных соединений

**Что сделать:**

- UI и engine слушают только loopback.
- На каждый запуск создавать случайные секреты отдельно для UI-сессии и engine.
- Доставлять UI bootstrap-секрет через native bridge, не через обычный URL, логи или постоянный файл.
- После обмена выдавать сессионную `HttpOnly`, `SameSite=Strict` cookie; имя cookie уникально для экземпляра.
- Проверять точный допустимый Host с портом.
- Для изменяющих запросов проверять Origin; произвольные origins не разрешать.
- Защитить чтение данных, настройки, файловые и медиамаршруты, а также управляющие endpoints.
- Engine требует отдельный токен во всех запросах.
- Отключить отладочные API-документы в production.
- Не выдавать произвольный файл по переданному пути: чтение аудио и экспортов разрешать через зарегистрированный объект приложения.
- Для внешних ссылок разрешить только ожидаемые `https`-адреса; опасные схемы отклонять.

**Приёмка:** отсутствующий/неверный токен, чужой Host/Origin, обращение напрямую к engine, обход путей и прямое чтение медиа отклоняются. При этом штатные аудиоплеер, экспорт и все экраны работают в настоящем WebView.

### 5.2. Сделать секреты доступными только для замены

**Что сделать:**

- Ответы API содержат `has_key`/`has_password` и источник настройки, без полного значения.
- Контракт изменения:
  - поле отсутствует — сохранить;
  - непустое значение — заменить;
  - отдельное явное действие — удалить.
- Не использовать пустую строку одновременно как «не менять» и «удалить».
- Поля секретов при открытии настроек пустые, рядом показан статус.
- Переменные окружения показывать как внешний источник; приложение их не изменяет.
- Хранить локальные секреты отдельно от обычных настроек, с защитой Windows DPAPI для текущего пользователя.
- Старые открытые секреты переносить только после успешной проверки нового хранения.
- Удалить секреты из логов, HTTP-ошибок, диагностических архивов и тестовых артефактов.

**Приёмка:** сохранение несекретной настройки не стирает ключ; замена/удаление работают; ключи не появляются в GET-ответах, HTML, логах и отчётах.

### 5.3. Сделать настройки устойчивыми к сбоям

**Почему:** запись JSON через перезапись файла и независимые read-modify-write могут терять данные.

**Что сделать:**

- Ввести единый сервис настроек с блокировкой полного цикла изменения.
- Писать во временный файл в том же каталоге, затем атомарно заменять.
- Поддержать версию формата и последнюю корректную копию.
- Повреждённый файл не трактовать как пустые настройки с последующей тихой перезаписью.
- Метаданные YouTube перенести в SQLite с идемпотентной миграцией.
- Не копировать старые открытые секреты в обычные резервные JSON.

**Приёмка:** конкурентные обновления разных полей сохраняются; прерывание записи, повреждённый JSON, нехватка места и повторная миграция не приводят к молчаливому сбросу.

### 5.4. Ограничить Gemini CLI

**Почему:** автоматическое одобрение инструментов в режиме `yolo` даёт больше полномочий, чем требуется транскрибатору.

**Что сделать:**

- Убрать `--approval-mode yolo`.
- Работать в отдельном временном каталоге с минимальным набором входных файлов.
- Использовать поддерживаемый CLI режим без произвольного выполнения инструментов.
- Если установленная версия не позволяет обеспечить нужные ограничения, завершать операцию понятной ошибкой.
- Добавить тайм-аут, отмену и очистку временных данных.

**Приёмка:** подготовленный текст во входном файле не приводит к выполнению shell-команд или изменению файлов вне рабочей области запроса. Небезопасного fallback нет.

## 8. Этап 6. Соблюсти границу UI/engine и ограничить расход ресурсов

### 6.1. Убрать тяжёлые импорты из UI

**Почему:** прогрев CUDA и некоторые пути диаризации нарушают заявленную архитектуру.

**Что сделать:**

- Перенести CUDA-прогрев, torch, GigaAM и NeMo в engine-процесс.
- Диаризацию вызывать через engine с идентификатором запуска, прогрессом и отменой.
- UI получает только состояние и результаты.
- Расширить проверку импортов на динамические и транзитивные пути.
- Проверять фактический `sys.modules` UI-процесса после запуска и выполнения сценариев.

**Приёмка:** открытие настроек, проверка компонентов, файловая обработка, пакет и диаризация не загружают torch/gigaam/nemo в UI. Облачный режим работает без этих пакетов.

### 6.2. Обрабатывать большие файлы без полного размещения в RAM

**Почему:** декодирование всего файла и дополнительные копии увеличивают память и задержку отмены.

**Что сделать:**

- Перейти на потоковое декодирование или временный PCM-файл с чтением ограниченных диапазонов.
- Передавать выбранный временной диапазон в ffmpeg до полного декодирования.
- Управлять ffmpeg через cancellable subprocess.
- Для облака готовить один временный источник и ограниченные части без многократного копирования всего файла.
- Получать длительность через ffprobe; включить его в поставку.
- Очищать частичные временные файлы при всех вариантах завершения.
- Хвост короче секунды не отбрасывать: при необходимости дополнять для модели, затем ограничивать таймкоды фактической длительностью.

**Приёмка:**

- Последнее короткое слово на хвосте присутствует.
- Диапазон внутри большого файла обрабатывается с правильными таймкодами.
- Отмена останавливает ffmpeg и освобождает временные данные.
- Для одного и трёх часов аудио память декодера не растёт пропорционально длительности.
- Отдельно учитывать память модели и накопленного текста, чтобы измерение было содержательным.

### 6.3. Проверить точность сегментов и спикеров

**Почему:** длинный сегмент GigaAM может охватывать смену говорящих.

**Что сделать:**

- Добавить контрольный набор с короткими репликами и сменой спикеров.
- Измерить ограничения текущих сегментов.
- Не делить текст между спикерами произвольно.
- В документации обозначить ограничения таймингов и диаризации.
- Выравнивание текста по словам оформить отдельным последующим улучшением, если контрольный набор покажет необходимость.

**Приёмка релизных исправлений:** прежняя точность не ухудшилась; ограничения описаны; нет заявлений о точности, которую тесты не подтверждают. Полноценное word alignment не является обязательной частью этого исправительного релиза.

## 9. Этап 7. Переделать установку и обновление окружений

**Приоритет: блокирует публичный релиз.**

Основные области: `launcher/Slysh.c`, `installer/Slysh.iss`, скрипты сборки и runtime setup.

### 7.1. Обеспечить первый запуск без сети

**Почему:** скопированная `.venv` содержит абсолютный путь машины сборки. Её восстановление через сетевой `uv sync` не обеспечивает автономный запуск.

**Целевая схема:**

- Не поставлять готовую `.venv` с путями машины сборки.
- Поставлять закреплённые версии Python, uv, ffmpeg/ffprobe, необходимые wheels и manifest с хешами.
- Включить все зависимости базового интерфейса; лёгкие компоненты YouTube также подготовить для локальной установки.
- Учесть WebView2: Setup содержит необходимый автономный пакет runtime и устанавливает его при отсутствии совместимого runtime.
- При первом запуске создавать окружение непосредственно в его окончательном пути.
- Устанавливать базовые пакеты только из локального wheelhouse, без обращения к индексам.
- Dev-зависимости в пользовательскую поставку не включать.
- Отсутствие моделей не мешает открыть интерфейс и настроить облачный провайдер.

### 7.2. Разделить базовое и тяжёлое окружения

**Что сделать:**

- Для установленной версии использовать отдельные окружения UI и engine.
- Engine запускается явным путём Python своего окружения.
- Хранить окружения в версионированных каталогах по fingerprint состава.
- Новое окружение создавать сразу в окончательном каталоге; не переносить готовую venv между путями.
- После успешной проверки атомарно переключать manifest активного окружения.
- Старое рабочее окружение сохранять до успешного запуска нового.
- При ошибке установки оставлять прежний рабочий вариант.
- Выбранные extras хранить явно; обновление не должно незаметно убирать диаризацию или другие компоненты.
- Для запуска из исходников сохранить поддержку существующей общей `.venv`.
- Добавить отдельную команду восстановления компонентов: успешный импорт torch сам по себе не означает актуальность всего окружения.

**Приёмка:** обновление UI не удаляет тяжёлые пакеты; ошибка загрузки/установки сохраняет рабочий вариант; повторная установка безопасна; облачный режим не создаёт engine-окружение.

### 7.3. Сделать сборку воспроизводимой и безопасной для предыдущего результата

**Что сделать:**

- Проверять исходники ffmpeg и остальные входные файлы до удаления чего-либо.
- Собирать новый payload во временном каталоге; прежний успешный payload сохранять до окончания проверок.
- Пересобирать launcher из текущего исходного кода.
- Проверять exit code каждой команды.
- Закрепить версии и хеши загружаемых инструментов.
- Использовать lock-файл без его неявного изменения.
- Записывать `version.json` в UTF-8 без BOM; чтение сделать совместимым со старыми файлами с BOM.
- Хранить единый источник версии и адреса GitHub-репозитория.
- Проверять payload после размещения в другом каталоге.
- Проверять отсутствие секретов, пользовательских БД, локальных моделей и абсолютных ссылок на машину сборки.

### 7.4. Исправить обновление приложения

**Что сделать:**

- Не создавать маркер первого запуска при обычном обновлении.
- Сохранять настройки, ключи, модели, записи и БД.
- Перед заменой файлов корректно закрывать работающий экземпляр.
- Не смешивать состояние проверки версии и текущей загрузки.
- Для запуска скачанного Setup требовать опубликованный SHA-256 и совпадение хеша.
- При отсутствии digest можно показать информацию о релизе, но нельзя автоматически запускать непроверенный файл.
- Проверять HTTPS и разрешённые адреса скачивания.
- Не пересылать GitHub-токен на произвольный URL или через междоменные редиректы.
- Повреждённый/оборванный файл не считать готовым обновлением.

**Примечание:** SHA-256 проверяет соответствие опубликованному артефакту. Цифровая подпись Setup и SmartScreen — **вне плана продукта** ([`PRODUCT_OUT_OF_SCOPE.md`](PRODUCT_OUT_OF_SCOPE.md)).

### Приёмка установщика

На чистых Windows 10 и 11 x64 проверить:

1. Нет Python, uv, ffmpeg и заранее подготовленного окружения.
2. Сеть отключена, кэши пустые.
3. Установка и первый запуск интерфейса успешны.
4. Путь содержит пробелы и кириллицу.
5. Запуск обычным пользователем.
6. Установка тяжёлых компонентов, отмена и повтор после сбоя сети.
7. Обновление версии с готовыми моделями, ключами и расшифровками.
8. Сбой обновления с возвратом к рабочему состоянию.
9. Удаление и повторная установка с соблюдением выбранного пользователем сохранения данных.
10. Отсутствие оставшихся процессов и неожиданных обращений к путям машины сборки.

Зелёный smoke на машине разработчика не заменяет эту проверку.

### Изменения контрактов, которые необходимо согласованно реализовать

| Область | Новый контракт |
|---|---|
| Запуски | `run_id`, адресная отмена, защита от устаревшего результата |
| Редактор | Ревизия, конфликт `409`, сохранение черновика |
| Спикеры | Постоянный ключ отдельно от имени |
| Запись | Раздельные состояния захвата/ASR, фаза `finalizing` |
| Пакеты | `completed_with_errors`, счётчики и причина паузы |
| Секреты | Признак наличия; сохранить/заменить/удалить без чтения значения |
| HTTP | Аутентификация UI/engine, проверка Host/Origin |
| Установка | Manifest активных окружений, автономное базовое окружение |

Существующие пользовательские БД должны мигрировать без потери текста, имён, путей и настроек. Миграции выполняются транзакционно, повторный запуск безопасен. Откат к старому приложению производится восстановлением соответствующей резервной БД; открывать новую схему старой версией без проверки нельзя.

### Обязательные уровни проверки

| Уровень | Что доказывает |
|---|---|
| Unit/regression | Каждый подтверждённый дефект исправлен |
| HTTP + настоящий subprocess | IPC, отмена, тайм-ауты и очистка процессов работают вместе |
| Frontend automation | Черновики, polling, переключение заданий и настройки устойчивы к гонкам |
| Настоящий WebView | Авторизация, аудиоплеер, диалоги и закрытие окна работают в продукте |
| Модельные smoke-тесты | GigaAM/faster-whisper действительно распознают, а не только проходят заглушки |
| Устройства | Микрофон и loopback сохраняют корректное аудио |
| Длительные сценарии | Нет линейного роста памяти, потери хвоста и зависшей финализации |
| Чистая Windows | Setup автономен и не зависит от машины разработчика |
| Миграции | Старые пользовательские данные сохраняются |

Для сетевых провайдеров обязательны контрактные тесты: успех, 401/403, 429, 5xx, timeout, некорректный ответ и отмена. Реальную платную проверку выполнять только с предоставленными тестовыми ключами и согласованным лимитом расходов. Отсутствие такой проверки явно указать.
