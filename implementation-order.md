# Рекомендуемый порядок реализации (после аудита)

**Статусы выполнения:** [`implementation-status.md`](implementation-status.md) (обновляется после каждой итерации).

Документ дополняет [`plan-fix.md`](plan-fix.md): не отменяет его цели, но **разделяет работу на волны** с разным масштабом и риском. Основано на сверке кода `Slysh-prod` / копии GPT и артефактов в `.review/`.

**Принципы:**

- Сначала подтверждённые дефекты с малым diff и высоким ROI; архитектурные блоки — отдельными итерациями.
- Каждая волна сдаётся с зелёным обязательным pytest (без сети/моделей) и краткой записью в `wiki/log.md` при переносе в prod.
- Не смешивать в одном PR: «точечный багфикс» и «новый installer runtime».

---

## Сводка волн

| Волна | Фокус | Ориентир | Блокирует |
|-------|--------|----------|-----------|
| **0** | Основа тестов | 0.5–1 дн. | Всё остальное |
| **A** | Корректность и потеря данных | 3–7 дн. | Стабильное ежедневное использование |
| **B** | Надёжность процессов и UX данных | 1–2 нед. | Уверенная отмена/закрытие/настройки |
| **C** | Job runtime (упрощённый) | 1–2 нед. | Параллельные сценарии без гонок |
| **D** | Публичная безопасность API и секреты | 1–2 нед. | Публичный релиз (часть 1) |
| **E** | Установщик и offline-first | 2–4+ нед. | Публичный релиз (часть 2) |
| **F** | CI, документация, лицензии | параллельно с D–E | Сопровождение репозитория |

Полный `run_id` + общий планировщик из plan-fix §1.1 — это **волна C**, а не обязательный префикс к волне A.

## Волна 0. Основа проверки

**Цель:** тесты проверяют код копии, а не editable-путь другой директории.

1. Зафиксировать baseline: `git status`, diff пользовательских правок vs аудита.
2. В conftest / скрипте запуска: `PYTHONPATH` → `...\Slysh-prod-GPT\src`, изолированный `GIGAAM_DESKTOP_HOME`.
3. Assert в начале прогона: `slysh.__file__` под ожидаемым `src`.
4. Разобрать 8 исходных падений pytest по plan-fix §0.2 (отдельные коммиты/логические группы):
   - заглушки диаризации и `cancelled=None`;
   - `JsApi` / `open_url`;
   - тест секретов — через исправление API, не ослабление assert;
   - streaming-тест: сегмент до завершения + тайм-аут терминала;
   - installer layout — smoke в другом пути, не привязка к машине сборки.
5. `.review/` в `.gitignore`; ценные сценарии перенести в `tests/` без личных данных.

**Выход:** полный обязательный pytest зелёный; таблица «было 8 fail → причина → что сделано».

**Не делать в волне 0:** переписывание engine/job runtime.

## Волна A. Блокеры корректности (высокий ROI)

Реализовать **в указанном порядке** — ниже учтены зависимости.

### A1. Deadlock установки и обновлений

- **Файлы:** `src/slysh/runtime_setup.py`, `src/slysh/updates.py`.
- **Суть:** не вызывать `setup_status()` / `download_status()` под уже захваченным `threading.Lock`; разделить «снимок состояния под lock» и «сборку ответа».
- **Тест:** повторный `start_engine_install` / `start_download` с тайм-аутом (как в `.review`: `install_repeat_deadlock`, `updates_repeat_deadlock`).
- **Зависимости:** нет.

### A2. Отмена engine не ломает следующий чанк

- **Файлы:** `src/slysh/engine_server.py`, при необходимости `engine_client.py`.
- **Суть:** глобальный `cancelled` Event — причина пустых чанков после отмены job A перед job B; scope отмены per-operation или сброс при новом `/transcribe_chunk` / session id.
- **Тест:** сценарий из `.review` `cancel_sequence`.
- **Зависимости:** нет (можно параллельно с A1).

### A3. Пакет файлов в режиме `cloud_only`

- **Файлы:** `src/slysh/batch_runner.py`, `src/slysh/api.py` (`_ensure_engine_url`, `_start_asr_job` / общий выбор исполнителя).
- **Суть:** тот же маршрут, что одиночный файл: облако/Gemini CLI без `ensure_engine` при remote-модели.
- **Тест:** заглушки remote, как `cloud_batch` в `.review`.
- **Зависимости:** минимальный общий helper «как запустить job» (не полный §1.1 plan-fix).

### A4. `on_error=stop` и итог пакета

- **Файлы:** `src/slysh/batch_runner.py`, `src/slysh/batch_rules.py`, `db.py` / статусы batch.
- **Суть:** файловая ветка как YouTube: `break` + `paused` с причиной; не ставить `COMPLETED`, если были ошибки и политика stop; ввести `completed_with_errors` / счётчики (plan-fix §2.2).
- **Тест:** `stop_on_error` из `.review`.
- **Зависимости:** A3 желательно раньше (один стиль обработки job).

### A5. Коллизии экспорта в пакете

- **Файлы:** `src/slysh/batch_runner.py`, `src/slysh/export.py` (`unique_export_path` уже есть).
- **Суть:** в fixed export dir не использовать голый `stem.fmt` для разных исходных путей с одним именем файла.
- **Тест:** два `same.wav` из разных каталогов → разные файлы, оба сохранены (`batch_export` в `.review`).
- **Зависимости:** нет.

### A6. Спикеры: стабильный ключ в сегментах

- **Файлы:** `db.py` (миграция), `api.py` (`rename_speakers`, отдача сегментов), `web/js/editor.js`, `legacy.js`, экспорт.
- **Суть:** `segments.speaker` = ключ; имя только в `speakers`; не вызывать `apply_speaker_names`, подменяющую ключ текстом.
- **Тест:** двойное переименование (`speaker_rename_twice`); Unicode; экспорт.
- **Зависимости:** резервная копия БД в тесте миграции; **до** массовых правок редактора (волна B).

### A7. Секреты: не отдавать полное значение

- **Файлы:** `src/slysh/providers.py`, `api.py`, `web/js/shell.js`, `secret-field.js`, локали.
- **Суть:** `has_key` / tail / источник; PUT: omit = сохранить, непустое = заменить, явное удаление.
- **Тест:** регрессия на GET settings/providers; сохранение несекретного поля не стирает ключ.
- **Зависимости:** нет.

### A8. Live/meeting: не ставить `completed` при ошибке ASR

- **Файлы:** `src/slysh/api.py` (`live_stop`, meeting stop), состояние capture vs transcription.
- **Суть:** разделить «запись сохранена» и «расшифровка успешна»; фаза `finalizing` (минимально — failed + сохранённое аудио, без ложного completed).
- **Тест:** mock remote/engine error после stop; двойной stop.
- **Зависимости:** нет для минимального фикса; полный §3 plan-fix — волна B.

### A9. Markdown/YAML в экспорте

- **Файлы:** `src/slysh/export.py`.
- **Суть:** нормальное экранирование YAML-скаляров (библиотека или безопасный литерал); тест с Windows-путём и кавычками.
- **Зависимости:** нет.

### A10. Gemini CLI без `yolo`

- **Файлы:** `src/slysh/gemini_cli.py`.
- **Суть:** убрать `--approval-mode yolo`; тайм-аут, temp dir, отмена.
- **Тест:** контрактный (аргументы subprocess / mock).
- **Зависимости:** нет.

### A11. Граница UI: CUDA warm-up и диаризация

- **Файлы:** `src/slysh/api.py`, `batch_runner.py`; перенос в engine по мере возможности.
- **Суть:** убрать `warm_cuda_cache` из UI; диаризация — через engine HTTP (можно урезанный endpoint в той же волне, полный §6.1 — волна C).
- **Тест:** `tests/test_ui_imports.py` + сценарий «старт без torch в UI».
- **Зависимости:** желательно после A2 (engine живёт стабильнее).

**Критерий приёмки волны A:** targeted-сценарии из `.review` зелёные; регрессии в `tests/`; без обязательного offline Setup.

## Волна B. Надёжность и UX данных

### B1. Редактор: dirty, job generation, поздние ответы

- **Файлы:** `web/js/editor.js`, API save transcript (при необходимости ревизия).
- **Минимум:** черновик per `job_id`, не перезаписывать при polling/switch; проверка `currentJobId` перед apply.
- **Расширение:** ревизия + `409` (plan-fix §4.1).
- **Зависимости:** A6 (спикеры в сегментах).

### B2. Атомарные настройки

- **Файлы:** `compute.py` / единый settings service, миграция YouTube metadata в SQLite (plan-fix §5.3).
- **Зависимости:** A7 (секреты отдельно от JSON).

### B3. Завершение subprocess и тайм-ауты (часть plan-fix §1.3)

- **Файлы:** `app.py`, `api.py`, spawn engine.
- **Не обязательно сразу:** полный watchdog 10 мин; достаточно PORT-wait, join engine on exit, kill tree owned by app.
- **Зависимости:** A2.

### B4. Live buffer (plan-fix §3.2) — поэтапно

1. Очередь из callback, запись вне callback.
2. Сериализация pause/stop.
3. Тесты pause/resume на синтетике.
4. Длительные 10+ мин — **manual release matrix**, не gate каждого PR.

### B5. `open_path` / reveal

- **Решение продукта:** 404 для отсутствующего файла vs текущий `resolve_open_target` (plan-fix §0.2 п.3). Зафиксировать в API docs и тесте **после** решения.

## Волна C. Упрощённый job runtime (вместо полного §1.1 с первого дня)

Цель волны C — закрыть гонки без переписывания всего приложения.

1. **Очередь:** один активный локальный ASR + один активный remote worker (как в plan-fix, без параллелизма).
2. **Идентификатор запуска:** `run_id` или monotonic `attempt` в БД; отбрасывать callback с устаревшим id.
3. **Отмена:** per-job в UI + scoped cancel в engine session.
4. **Повторный старт:** идемпотентность `POST .../start` для running job.
5. Позже (отдельная итерация): single-instance lock (plan-fix §1.4).

**Не включать в первую итерацию C:** параллельные облачные job, сложный планировщик записи+пакета (достаточно mutex live vs batch из plan-fix §1.1 политики).

## Волна D. Публичный релиз — безопасность

Порядок внутри волны:

1. Loopback-only + токен engine (все запросы).
2. UI session: bootstrap через pywebview bridge, cookie `HttpOnly` / `SameSite=Strict`.
3. Host/Origin на mutating routes.
4. Закрыть path traversal на медиа/файлах.
5. DPAPI для локальных секретов (после A7 контракта API).
6. Отключить debug OpenAPI в production-сборке.

**Приёмка:** чеклист в **настоящем WebView** (plan-fix §11); curl с чужим Host — отказ.

## Волна E. Установщик и обновление

Строго после стабилизации A (+ желательно B3):

1. Воспроизводимая сборка payload (plan-fix §7.3).
2. Без vendored `.venv` с абсолютными путями; wheelhouse + локальный install.
3. WebView2 offline в Setup.
4. Раздельные UI/engine env по fingerprint (§7.2) — отдельный подпроект.
5. Обновление: SHA-256, не ломать first-run marker, сохранение данных (§7.4).
6. Матрица чистых Windows 10/11 — **обязательна для релиза**, не для merge волны A.
