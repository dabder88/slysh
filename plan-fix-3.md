### Сохраняемые решения владельца

### Доказательства и ограничения аудита

Воспроизведены в изолированных проверках без записи файлов:

1. Гонка между чтением сегментов и ревизии при диаризации возвращает старый текст.

3. Поздний ответ сохранения A меняет глобальную ревизию редактора B, хотя его текст уже защищён.

## 3. F3-01 — атомарный снимок сегментов и ревизии

### Что и почему

Ориентиры: `src/slysh/speakers.py:92–95`, методы сегментов в `src/slysh/db.py`.

Текущий код отдельно читает сегменты, затем их ревизию. Если между чтениями сохраняется правка, он получает новую ревизию для старого текста и успешно записывает старую копию. Старый сценарий восстановления snapshot при ошибке уже исправлен; его не нужно возвращать.

В аудите: между чтением сегментов и ревизии записан `USER EDIT`; после применения диаризации в БД остался `OLD`.

### Как исправить

1. Добавить метод БД, возвращающий сегменты и соответствующую ревизию под одной блокировкой/в одной согласованной транзакции. Не держать эту блокировку во время работы модели.
2. До вызова backend получить исходный атомарный снимок.
3. После backend получить текущий атомарный снимок и проверить, что разметка всё ещё относится к тем же сегментам.
4. Совместимыми считать сегменты с теми же устойчивыми ID, порядком и временными границами. Если слой модели не передаёт ID, внутри операции сохранить исходные ID и проверить их в БД. Одного совпадения количества недостаточно.
5. Если изменился только текст, разрешить применить метки к **текущему** тексту. Изменённые пользователем привязки спикеров не перезаписывать устаревшим результатом; при таком конфликте отклонять результат операции.
6. Применять метки одной транзакцией с проверкой ревизии текущего снимка. Если после снимка появилась новая запись — вернуть конфликт, ничего не перезаписывать.
7. При ошибке, отмене или конфликте не восстанавливать старый текст. Показать понятное сообщение с возможностью повторить диаризацию.

### Тесты

- **Race-before-apply:** управляемым барьером остановить операцию после атомарного снимка; сохранить новый текст; продолжить применение. Ожидание: конфликт, новый текст сохранён.
- **Text-only-during-model:** backend ещё работает, пользователь меняет только текст; после модели получен новый снимок. Ожидание: метки применены к новому тексту, либо явный конфликт при дополнительной гонке.
- **Structure-change:** изменить порядок/временные границы или заменить сегмент при неизменном количестве. Ожидание: результат диаризации отклонён.
- **User-speaker-change:** пользователь меняет спикера во время обработки. Ожидание: его изменение не затёрто.
- Повторить прежний тест ошибки/отмены backend: сохранённый текст остаётся новым.

Использовать SQLite в памяти или отдельную временную БД и Events/barriers; не полагаться на случайные задержки.

**Приёмка:** отсутствует пара «старые сегменты + новая ревизия»; любое применение либо соответствует проверенному снимку, либо отклоняется без потери данных.

## 4. F3-02 — обработка короткого хвоста записи

### Что и почему

Ориентиры: `src/slysh/live_buffer.py:83,93`, вызовы pause/stop/finalize диктофона и встречи.

Файловая обработка уже передаёт хвост короче секунды. В LiveSession порог остался: после 8000 отсчётов при 16 кГц `flush()` возвращает `None`. Последнее слово может присутствовать в WAV, но отсутствовать в расшифровке.

### Как исправить

1. `take_pending_tail()` возвращает любой непустой остаток и очищает соответствующий pending.
2. `flush()` закрывает WAV, возвращает любой непустой остаток и очищает pending. Повторный вызов возвращает `None`, чтобы хвост не распознавался дважды.
3. Если конкретному backend нужна минимальная длина, дополнять нулями только его вход. Сохранять отдельно фактическую длину хвоста и ограничивать таймкоды ею.
4. Смещения считать в отсчётах/миллисекундах. Дополнение модели не увеличивает продолжительность записи.
5. Проверить все ветки pause/resume/stop для live и meeting, не только метод буфера.

### Тесты

- Параметризованный unit: 0, 1, 3200, 8000, 15999, 16000 отсчётов. Ожидание: None только для нуля.
- `flush()` дважды: второй вызов не возвращает те же данные.
- Pause → resume → stop: каждый входной отсчёт передан ровно один раз, смещения непрерывны.
- 20,5 и 40,5 секунды: полный chunk плюс последний остаток переданы обработчику.
- Интеграционный тест finalize с backend-заглушкой, выдающей текст только на последнем коротком блоке. Проверить наличие этого текста в итоговой БД.
- При padding проверить, что ни один конец сегмента не выходит за реальную длительность.

**Приёмка:** непустой хвост не исчезает из обработки и не дублируется. Существующее исправление файловой ветки остаётся зелёным.

## 5. F3-03 — явное завершение meeting при переполнении pending

### Что и почему

Ориентиры: `src/slysh/meeting_capture.py:_flush_mix` около строки 584, `src/slysh/audio_ingest.py:_run`, обработка overflow диктофона в API.

В диктофоне LiveBufferOverflowError превращается в сигнал остановки. В meeting исключение из `session.push(mixed)` попадает в общий catch, только логируется, после чего очередь продолжает обработку. Переполненный блок уже записан в WAV, но отсутствует в pending. Это может дать неполную расшифровку без корректного статуса ошибки.

### Как исправить

1. В пути meeting перехватывать LiveBufferOverflowError и передавать его контроллеру захвата через явный callback ошибки.
2. При первом overflow атомарно установить состояние ошибки и запросить остановку захвата. Повторные callbacks не запускают повторную финализацию.
3. Не выполнять ожидание завершения текущего ingest-потока из этого же потока. Остановку/закрытие устройств выполняет управляющий поток.
4. Закрыть WAV штатно и сохранить записанную доступную часть. Уже распознанный текст оставить.
5. Итоговое задание не считать completed. Показать причину и разрешить повторную файловую расшифровку сохранённого WAV после освобождения ресурсов.
6. Не расширять RAM cap автоматически и не проглатывать ошибки хранения аудио общим логированием.

### Тесты

- Установить небольшой cap и замедлить ASR заглушкой; передавать блоки meeting до переполнения.
- Проверить: overflow callback вызван один раз; stop запрошен; ошибка доступна API; дальнейший захват остановлен; финализация не зависла.
- Открыть сохранённый временный WAV и сравнить с фактически записанными блоками, включая блок, на котором возникло переполнение.
- Убедиться, что итог не completed и доступен повтор ASR из сохранённого файла.
- Повторить аналогичный тест диктофона, чтобы не сломать существующий путь.

**Приёмка:** переполнение meeting наблюдаемо для пользователя и не превращается в молчаливое продолжение расшифровки с пропусками. Реальные устройства для обязательного теста не нужны.

## 6. F3-04 — согласовать offline bootstrap и wheelhouse

### Что и почему

Ориентиры: `launcher/Slysh.c:719`, `Slysh.bat:41`, `src/slysh/offline_bootstrap.py`, скрипт payload, `tests/test_offline_bootstrap.py`.

Команда offline sync не содержит --no-dev, а wheelhouse экспортирован без dev. В payload присутствуют требования pytest/httpx, но соответствующих wheels нет. Кроме того, proxy_tools поставляется sdist, которому нужно окружение сборки. Проверка наличия строки --offline и фиктивного a.whl не проверяет возможность установки.

### Как исправить

1. Для установленной версии сформировать закреплённый набор требований **только UI/runtime**, без dev и extras engine. Согласовать его с утверждённым lock-файлом.
2. На машине сборки подготовить полный набор wheels для поддерживаемой Windows x64/Python 3.12. Исходные архивы заранее превратить в wheels, включая proxy_tools. Подготовить wheel самого slysh, если пакет устанавливается в окружение.
3. Для offline bootstrap установленной версии создавать новое окружение bundled Python в окончательном каталоге, затем устанавливать подготовленные wheels без индексов и сетевого разрешения зависимостей. Рекомендуемый контракт — pinned requirements с локальным wheelhouse через `uv pip sync --python <venv-python> --no-index --find-links <wheelhouse> <requirements>`.
4. Launcher, BAT установленной версии и Python-helper должны использовать один и тот же manifest/контракт. Режим запуска исходного клона отделить от установленной копии.
5. При отсутствующем wheel выдавать понятную ошибку повреждённой/неполной поставки. Не выполнять незаметный fallback к сети в offline-ветке.
6. Не включать engine и модели в базовую установку и не менять существующие engine slots.

### Проверка без VM и без установки WebView2

В отдельном временном каталоге подготовить минимальную копию компонентов bootstrap. Не использовать существующую .venv и кэш разработчика.

- Задать пустые UV_CACHE_DIR и отдельные TEMP/TMP; отключить автоматическое скачивание Python; запретить сеть режимами uv и тестовым ограничением доступа.
- Создать окружение bundled Python из wheelhouse.
- Проверить импорт slysh, FastAPI, pywebview, sounddevice, soundfile и numpy; проверить предусмотренные базовым manifest дополнительные пакеты.
- Проверить отсутствие dev/engine-зависимостей в базовой установке.
- Переместить исходный payload **до создания окружения** в путь с пробелами и кириллицей, повторить bootstrap.
- Повторить запуск с уже корректным окружением: не должно быть ненужной переустановки.
- Удалить один wheel из тестовой копии: bootstrap должен завершиться явной ошибкой без доступа к сети и без выдачи успеха.

**Приёмка:** с пустым кэшем создаётся работоспособное Python/UI-окружение. Открытие окна на машине без WebView2 и сети не является критерием этого пункта. Тест выполняется вне пользовательской установки.

## 7. F3-05 — завершить миграцию proxy password без plaintext backup

### Что и почему

Ориентиры: `src/slysh/http_proxy.py:_read_stored_proxy_password`, `src/slysh/api.py:2250–2251`, `settings_store.py`.

Миграция провайдеров синхронизирует очищенный backup, затем миграция proxy сохраняет settings обычным способом. При этом прежний JSON с открытым паролем снова попадает в .bak. Разрешённое раскрытие секрета авторизованному UI не разрешает такое хранение.

### Как исправить

1. Объединить миграцию ключей провайдеров и proxy в согласованный процесс. Если остаются самостоятельные ленивые миграции, каждая должна завершать очистку резервных файлов.
2. Сначала сохранить секрет в DPAPI и проверить чтение; затем убрать plaintext из settings.
3. Записать очищенный primary и безопасный backup под общей блокировкой настроек. Не выпускать plaintext обратно в .bak при следующем шаге миграции.
4. Учесть существующий backup: восстановление после повреждения primary не должно возвращать пароль в открытый JSON.
5. Ошибку записи/чтения защищённого хранилища сообщать явно; не удалять единственную рабочую копию секрета до успешного переноса.

### Тесты

- Legacy settings с одним вымышленным proxy password → полный порядок миграции приложения. Проверить отсутствие значения в primary, .bak и tmp; проверить его получение через защищённое хранилище.
- Одновременно legacy API-ключи и proxy password; повторить миграцию дважды.
- Повредить primary после миграции и восстановить из backup: настройки восстановлены, plaintext не возвращён.
- Сымитировать отказ DPAPI/записи: нет тихой потери ключа и ложного статуса успеха.
- Проверить standalone вызов миграции proxy, а не только общий bootstrap.

**Приёмка:** после успешной миграции все созданные открытые файлы не содержат тестовых секретов; авторизованный reveal продолжает работать.

## 8. F3-06 — ревизия редактора принадлежит заданию и версии черновика

### Что и почему

Ориентиры: `web/js/legacy.js:2094`, `saveSegments`, обработка 409, состояние черновиков `web/js/editor.js`.

Защита перерисовки работает, но segmentsRevision обновляется до проверки текущего задания. В воспроизведении у B была ревизия 9; ответ A с ревизией 2 не меняет текст B, но устанавливает его общую ревизию в 2.

### Как исправить

1. Хранить базовую серверную ревизию вместе с черновиком конкретного job_id. Не использовать один изменяемый номер для всех открываемых заданий.
2. В момент сохранения фиксировать job_id, generation черновика, отправленный текст и его базовую ревизию.
3. Ответ A обновляет сведения об A. Нельзя переносить его revision в текущее B ни в успешной ветке, ни после 409.
4. При успешном сохранении, если текущий черновик того же задания изменился во время запроса, сохранить его текст и dirty. Его базу можно продвинуть до ревизии успешного собственного PATCH, если не было другой серверной записи; это должно быть явной логикой, а не следствием общего присваивания.
5. На конфликте 409 не делать автоматический rebase старого черновика только заменой expected_revision. Сохранить локальный текст и показать конфликт. Повторное сохранение поверх чужих изменений требует явного решения пользователя.
6. Сериализовать сохранения одного задания либо игнорировать устаревшие ответы по идентификатору операции. Ответ GET после PATCH также проверять на актуальность.

### Тесты

- Сохранение A задержано; открыть B с revision=9; вернуть ответ A revision=2. Ожидание: B сохраняет revision=9, свой текст и dirty.
- То же для 409 и следующего GET задания A.
- Внести новые правки в A во время его сохранения. Ожидание: правки остаются dirty, следующий запрос содержит корректную базу.
- Два сохранения одного задания и ответы в обратном порядке: старый ответ не уменьшает ревизию и не очищает новый черновик.
- Серверное изменение + 409 + повторное нажатие Save: без явного разрешения конфликта серверный текст не затирается.

Использовать управляемые promises и настоящие функции редактора/состояния. Синтаксическая проверка JS не заменяет эти тесты.

**Приёмка:** текст, dirty, revision и состояние save относятся к одному и тому же заданию/черновику; отложенный ответ не меняет чужое состояние.

## 9. F3-07 — жизненный цикл временного PCM

### Что и почему

Ориентиры: `src/slysh/decode.py:202`, создание pcm_path и `_load_pcm_f32le`.

В finally удаляется media_tmp, но частичный pcm_path остаётся на отмене, ошибке ffmpeg и ошибке загрузки PCM. Повторные обработки способны накапливать большие временные файлы. Сам memmap соответствует согласованному объёму R10.

### Как исправить

1. Сделать владение pcm_path явным: до успешной передачи результата за файл отвечает decode.
2. При исключении, отмене, пустом/некорректном PCM закрыть процесс и файловые дескрипторы, затем удалить PCM в finally.
3. Для обычного ndarray удалить PCM сразу после чтения.
4. Для memmap закрывать отображение перед удалением файла. Предпочтительно предоставить явный контекст/close для результата и закрывать его во всех потребителях; finalizer оставить запасной защитой, а не единственным механизмом.
5. Не удалять файл, пока используются его views. Определить и протестировать границу владения при нарезке chunks.
6. Не скрывать постоянную ошибку очистки; логировать путь и причину без содержимого пользовательских данных.

### Тесты

- fake ffmpeg создаёт частичный PCM, затем отмена → процесса нет, PCM нет.
- Ненулевой exit code, ошибка запуска, нулевой размер и размер не кратный float32 → PCM удалён.
- Успешное чтение малого массива → PCM удалён, данные доступны.
- Успешный memmap на Windows → данные доступны до close; после close файл удалён.
- Прерывание потребителя посреди обработки chunks → контекст закрыт, файл удалён.
- Повторить несколько десятков коротких циклов ошибки/отмены в выделенном temp-каталоге: число оставшихся PCM равно нулю.

**Приёмка:** после любого завершённого сценария нет неиспользуемого PCM; успешный результат не обращается к преждевременно закрытому mapping.

## 10. Общая проверка и сдача

### Автоматические проверки

1. Добавить перечисленные регрессии в обязательный subset. Для offline bootstrap выделить отдельную проверку артефакта: fake wheels и поиск строк не являются заменой установки.
2. Запустить актуальный `run_plan_fix2_targeted_tests.ps1` с новыми проверками либо его согласованного преемника.
3. Запустить полный pytest в изолированном каталоге данных. Разделять ошибки тестовой инфраструктуры, несовместимые заглушки и реальные регрессии приложения.
4. Выполнить JS syntax check и новые поведенческие JS-тесты.
5. Повторить уже исправленные сценарии: auth .json без сессии → 401; файловый хвост 20,5 с; ошибка диаризации не восстанавливает OLD; поздний ответ A не стирает B; ошибки обязательных стадий пакета учитываются.
6. Для каждого native command в PowerShell проверять exit code. Не считать последнюю успешную команду доказательством успеха всего скрипта.

Тесты используют PYTHONPATH проверяемой копии, временный GIGAAM_DESKTOP_HOME и временный basetemp. Не закрывать пользовательские приложения ради тестов; убирать только созданные тестом процессы. Не вызывать реальные платные API.

### Сборка

После изменений runtime/UI/launcher пересобрать launcher, payload и Setup согласно текущим скриптам проекта. Не требовать старое имя Slysh-Setup.exe, если действующая схема выпуска уже использует Slysh-Setup-ru.exe и Slysh-Setup-en.exe: отчёт должен перечислить фактически выпущенные артефакты и не спутать их со старой сборкой.

Для каждого нового Setup передать полный путь, версию, размер, LastWriteTime и SHA-256. Зафиксировать соответствие src/web и payload; офлайн-проверку Python-окружения выполнять на компонентах этого payload.

### Отчёт исполнителя

Для каждого F3-xx:

- причина ошибки и итоговое поведение;

### Критерии принятия

- F3-01–F3-07 подтверждены соответствующими проверками.
- Нет потери пользовательского текста, молчаливого пропуска хвоста или overflow встречи.
- Нет подмены ревизии другого задания.
- Нет открытого proxy password в резервных настройках после успешной миграции.

- Ошибка/отмена декодирования не оставляет временный PCM.
- Существующие исправления не регрессировали; автоматические проверки имеют достоверный отчёт.
